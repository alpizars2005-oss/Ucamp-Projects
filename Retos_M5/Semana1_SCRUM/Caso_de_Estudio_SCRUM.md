# Definición del Caso de Estudio - SCRUM Semana 1

## Proyecto seleccionado

**Mochi Monchi - Sistema digital de pedidos e inventario**

El proyecto propone una herramienta para centralizar catálogo, pedidos, recetas, inventario de ingredientes y desechables, costos y reportes operativos. La idea es desarrollarla por etapas y ajustar las funciones conforme se prueben en el negocio.

## Justificación del uso de Scrum

Elegí Scrum porque este proyecto puede cambiar conforme se use en la operación real de Mochi Monchi. Aunque desde el inicio se conocen necesidades como pedidos, inventario y recetas, todavía hay decisiones que conviene validar con la práctica: qué información debe mostrarse, qué reportes son realmente útiles o cómo manejar nuevos productos y promociones.

Con Scrum puedo trabajar en entregas pequeñas, revisar cada avance y reorganizar prioridades sin tener que esperar hasta el final para saber si la solución funciona. También permite incorporar retroalimentación frecuente y reducir el riesgo de desarrollar funciones que después no sean necesarias.

Frente a un enfoque tradicional, este marco resulta más conveniente porque el proyecto tiene requisitos que pueden evolucionar y necesita adaptarse mientras se aprende del uso real del sistema.

## Matriz inicial de roles - Scrum Team

En este reto una misma persona asume temporalmente las tres responsabilidades, pero se mantienen separadas para distinguir decisiones de producto, facilitación de Scrum y trabajo de desarrollo.

| **Scrum Master** | Ángel Alfredo Alpizar Sánchez | Facilita el uso de Scrum, ayuda a mantener objetivos claros, identifica impedimentos y promueve que el trabajo avance con enfoque y mejora continua. |
| **Development Team** | Ángel Alfredo Alpizar Sánchez | Analiza, diseña, programa, prueba y documenta los incrementos. Organiza el trabajo técnico y busca que cada entrega tenga la calidad necesaria para ser útil. |

## Por qué el caso encaja con un marco ágil

- **Incertidumbre:** los requisitos se afinan al observar el uso real del sistema.
- **Retroalimentación:** cada incremento puede validarse antes de ampliar el alcance.
- **Valor temprano:** las funciones prioritarias pueden ponerse en uso desde los primeros sprints.

## Cobertura de la rúbrica

- **Proyecto claro:** se define un producto de software concreto y útil para la operación del negocio.
- **Justificación Scrum:** la elección se relaciona directamente con requisitos cambiantes, validación frecuente y adaptación.
- **Roles correctos:** se distinguen las responsabilidades de Product Owner, Scrum Master y Development Team en el contexto del proyecto.

## Resultado esperado

El caso de estudio queda preparado para continuar en las siguientes semanas con backlog, sprints e incrementos, manteniendo el mismo proyecto como hilo conductor del módulo.
